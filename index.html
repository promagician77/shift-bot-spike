How the Telegram UI works

Your spec describes a dashboard, settings, filters, and shift alerts. Here's how they look as inline-keyboard messages, which is the native Telegram way to build a bot UI without a separate web app:

📊 Dashboard
Status: 🟢 Monitoring
Auto-apply: ❌ Off
Check interval: 2 min
Checks: 12 | Shifts found: 5 | Errors: 1
⏸ Pause
🔄 Check now
⚙️ Settings
🔍 Filters
📋 Recent shifts
🚨 New shift available
📍 Brampton Warehouse A
📅 Monday 🕐 Morning
💰 $18/hr
✅ Apply now
❌ Skip

Every button press is handled by handleCallback() in telegram.mjs, which returns the next message to send. The whole UI is a state machine: dashboard → settings → filters, and back. It's easy to add screens because each one is a function that returns a message object.

Keeping the session alive

The most common reason bots get flagged isn't clever detection; it's that every check starts from a cold browser with no cookies, hits the login page, and loads the same sequence in 200ms flat. That pattern is obvious.

My approach, in the session manager:

  • Warm sessions: after the first login, save the cookies and localStorage. Every following check reuses them, so the site sees a returning user, not a new visitor.
  • Fingerprint rotation: a small pool of realistic browser profiles (viewport, timezone, user-agent). Each session uses one consistently, because a fingerprint that changes mid-session is a red flag.
  • Human timing: 400-900ms random delays between actions. Fast enough to not miss shifts, slow enough to not look scripted.
  • The webdriver flag: Playwright sets navigator.webdriver = true by default. The session manager removes it. Many WAFs check this first.
  • Retry with backoff: if a check fails (network, WAF challenge, timeout), wait and retry with growing delays instead of hammering the server.

For CAPTCHAs that can't be avoided, I use a solving service (2Captcha or CapSolver) as a fallback. The key is to minimize how often they appear by keeping the session warm and the behaviour realistic.

           │

│                         │  Applies user filters
└──────────┬──────────────┘
           │
┌──────────▼──────────────┐
│   Session manager       │  Playwright with warm cookies
│   (Playwright)          │  Fingerprint pool, human delays
│                         │  Retry with backoff
└──────────┬──────────────┘
           │
┌──────────▼──────────────┐
│   Target site           │  Login, scrape shifts, auto-apply
│   (AWS WAF / CAPTCHA)   │  CAPTCHA fallback via solving service
└─────────────────────────┘

What I'd ask you before starting

  1. One user or many? If it's just you, we store settings in a JSON file. If you're reselling access, it needs a database and per-user sessions.
  2. Where does it run? A VPS with a residential proxy is the safest. Cloud functions (Lambda, etc.) rotate IPs on every call, which is exactly what WAFs look for.
  3. How fast do shifts disappear? If they're gone in 30 seconds, auto-apply has to be instant and the check interval needs to be under a minute. If they last hours, we can be gentler on the site.
  4. Does the site have an API or mobile app? Sometimes the mobile API is less protected than the web UI. Worth checking before building the scraper.
